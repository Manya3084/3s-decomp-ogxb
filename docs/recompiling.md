# Recompiling

The tree aims to hold enough C to rebuild the game for another platform. This page says what that C covers, what a port has to supply itself, and how far the non-matching C can be trusted.

## What has C

- Game code. Every function of the game proper (`src/sf33rd/Source/Game`, `Common`, `AcrSDK`, and the Xbox-only files in `src/sf33rd/Source/XBOX`) has C, apart from two unreferenced functions behind an unused two-entry jump table at `0x25C3B8` (dead code between `effect_A9_init` and `Setup_EffD8_Pos`).
- The Xbox save system: the save menu (`SaveInit`, `SaveMove` and the `xb_SaveMenu*` states and steps, with their tables in C), the file side (`xb_SaveState*`: headers, reads and writes with their `XCalculateSignature` checks, the room checks on `U:`), and the three kinds' descriptors (system data, directions, replays).
- The Xbox platform layer: graphics (`flSetRenderState`, the render-state and blend mapping, texture and palette handles, `flLockTexture`/`flUnlockTexture`, the quad renderers, frame end and present), input (`xb_PADRead`, the stick and button conversion), the debug print layer, the XACT sound banks and voices, and start-up (`njUserInit`, `xb_InitGraphics`, `xb_InitVideoMemory`).
- CRI ADX and AIX (`src/cri`): the ADX decoders and header parsers (ADX, AHX, WAV, AU, AIFF, SPSD), streaming, AIX demux and playback, the `wx_ci` file layer and the `wxfic` directory cache, and the DirectSound voice writer (`mw_snd`).

A scan of the game's part of `.text` against every named range (sizes from `funcs.txt`, starts from `folded.json` and `xdk.txt`) finds no other unclaimed code: what remains between named functions is data (jump and switch-index tables), STL template instances, and the XDK sample code below.

## Data

Most of the game's initialized data is in C: the tables of the generated and hand-ported files, and the PS2 data files (`Com_Data.c`, `cmd_data.c`, the US message text and the rest), each compared with the XBE by `analysis-ps2map/portdata.py` and given the Xbox values where they differ (see [decompiling.md](decompiling.md#the-ps2-data-files)). The CRI tables are in C too: the SJ interfaces and UUIDs, the file device interfaces (`wx_ci`, `mf_ci`), the mwSnd and mwVSnd voice interfaces, the ADX key primes (`skg_prim_tbl`), the mu-law table, and the build strings.

The PS2 build's binary tables (`bin2obj`: the character tables, the `_asstbl_*` animation tables, the exchange, gauge, knock-back and damage-pause tables) are ported to `src/bin2obj` the same way, each checked against the XBE; two Xbox tables are shorter than the PS2 ones, and the sub-tables carry their Xbox addresses as `D_ADDR` names. The Xbox Live text (235 Japanese/English string pairs that `xb_SetupLiveLanguage` picks from at start-up) is in `xb_livetext.c`, and the CRI build strings are defined. The Japanese game text, which the PS2 tree does not have, is in `Message3rd/C_JPN`: the win, talk and end messages of the 20 characters and the system direction, extra and menu messages that `get_message_conn_data` reads through `D_0032C150` when the language is Japanese, one file per US file (`analysis-ps2map/jpnmsg.py`, 1319 tables, all matching). The Xbox-only tables of the platform layer are in C too (the shader file names and vertex declarations, the pad and trigger maps, the video modes, the pan and volume tables, the print palettes, the effect draw table), written by `analysis-ps2map/xbdata.py` from their C declarations and checked with `portdata.py`.

What the C declares and does not define comes from the XBE: the embedded assets (the 780 KB Shift-JIS glyph bitmap at `D_00334900` the print layer draws from, and the XACT sound banks `D_0032FD80` points at), the vtables of the STL and sample-code classes, the Live tables, and the XDK's own data. The kernel import slots (`D_00218DC0` and the others in the import table) are left out: a port calls its own functions for those. They are not in the tree, as the binaries are not; a port reads them from its own `sf33rd.xbe` at the addresses `config/sf33rd/symbols/data.txt` gives (or the `D_ADDR` in the name). `tools/xbe_tables.py` writes them to `build/xbe_tables.c` (about 180 tables, 1 MB, most of it the glyph bitmap and the sound banks; a table sized by the next known address can run past its end). Each table is sized from `data.txt`, the PS2 map, or the next address the tree knows. A table the C declares with pointer elements has each word written as a symbol plus offset (a function, a global the C defines, or another written table, so unnamed tables a pointer reaches are written too), which keeps it right where the image is not mapped at its own addresses; in other tables only a word equal to a known symbol's address is read as a pointer. The file's header lists every word read as a pointer and the ones that look like addresses but have no symbol (pointers into zero-initialized storage, and Live code). Zero-initialized globals need only storage.

## Folded bodies

Retail's linker merged identical functions into one body, so one address can carry several names (`analysis-ps2map/folded.json`). The C defines such a body under one of its names. Where a call keeps the body's address instead (`sub_0004384A`, the empty body 59 names share), nothing defines that `sub_` name. The relink places it by address; a port's linker needs an alias. `tools/fold_aliases.py` lists them from the compiled objects (`--format ld` for GNU ld `--defsym` options, `--format msvc` for `/ALTERNATENAME`): 22 aliases, each a cdecl function, so the declared parameters may differ harmlessly. The names it warns about have no C at all: they are XDK functions the port supplies.

## What a port supplies

- The XDK libraries: D3D, DSOUND, XACT, XAPI, XGRAPHICS, the C runtime. Their names and addresses are in `config/sf33rd/symbols/xdk.txt` (see [xdk.md](xdk.md)); none of their code is in the tree. The game calls D3D through `D3DDevice__*` header wrappers and the `xb_` wrappers in `xb_012146.c`; a port maps those to its own renderer.
- The copies of XDK sample code (`CXB*`, `XBUtil_*`, `XBInput_*`, `CXHV*`, `_xbOnlineTask`), which have no C (see [decompiling.md](decompiling.md)). The game uses `XBInput_CreateGamepads`/`XBInput_GetInput` for pads and `CXBFont` for the sample font.
- The Xbox Live code (`src/sf33rd/Source/XBOX/xlive`, `NetSync`, the online objects) has C: the Live work's frame (`xb_XLIVE_WORK_CLASS_Run`) and its modes, sign-on, the Join, Host and quick-match state machines with their screens (the work's virtual methods included), the session search and QoS probes, the friends, players, stats, voice-mail and online-status pages, the in-match start and stats menus, voice chat, the NetSync engine (its state machine, frame queue and message handler) and the system-link connect. What it calls and does not define is XDK code: the XOnline, XNet and XHV functions and the XDK sample classes and STL containers listed below, which have names but no C. The parts offline play runs:
  - at start-up, `xb_LiveWork_Init` (with `xb_SetupLiveLanguage` and `xb_XLIVE_WORK_CLASS_ResetState`) and `xb_InitOnlineBuffers`, which sets up the Live text layer (`xlive_font.c`);
  - every frame, the debug print layer, which draws its glyphs through `xb_xlive_font_DrawQueue`;
  - before each match, `Game01`'s settings exchange (`xb_NetSync_Step`, `xb_NetSync_CheckPlayers` and the message queue), which writes `save_w[2]` and `permission_player` even offline.

  The rest is reached only with the online flag set, or once the player opens the Xbox Live menu (`xb_Menu_XboxLive`, which sets the Live work's `+0x2330`, `+0x235C` or start-menu `+0x6D` state that `xb_RunFrame`'s `xb_OnlineUpdate`, `xb_OnlineMenuDraw` and `xb_LiveWork_Update24C0`/`Poll24C0` test). `xb_NetSync_ParsePacket` only sees messages from a peer. A port can stub all of that; the Xbox Live menu (`xb_Menu_XboxLive`, step 14 of `Menu_Jmp_Tbl`) reaches the Live work only through `xb_LiveWork_Step`. The Live work object's constructor and destructor (`xb_XLIVE_WORKBASE_CLASS_ctor`/`dtor`) and its members' have C, without their C++ exception frames.

## Checking what a port has to supply

`tools/port_link.py` compiles every file of `src/` with the host gcc (`-m32`), with `build/xbe_tables.c` when `tools/xbe_tables.py` has written it, and lists every global the objects reference and none defines, by kind. With the tables written, all of them compile, nothing is defined twice, and what is left is what this page lists: about 275 XDK functions and kernel imports (D3D, DirectSound, XACT, XAPI, XOnline), a dozen C runtime functions and compiler helpers, the fold aliases above, and about 115 XDK sample and STL functions. No data, no game function and no Live function is left. `-v` lists the names.

## How far the C can be trusted

10329 placed functions build to retail's bytes. 462 more have C that does not. For those, `tools/behave.py` runs the C and the retail body side by side on random inputs (see [relink.md](relink.md#checking-differing-code-by-running-it)). A sweep of them and of the unplaced helpers, 473 names (200 trials each, October 2026), gave:

- 295 pass: the C and retail leave the same memory and return the same value on every trial both completed. 21 of them pass only with `--fill-null`, which points the null globals they read at scratch buffers.
- 102 have no comparable trial, even with `--fill-null`: both sides crash on every input. Many are game functions that read through global work pointers, which are null in the unstarted image the harness maps (`check_6` and the other command checks through `waza_ptr` and `cmd_tbl_ptr`); others follow pointers inside the random argument buffers or call into the XDK. These are the functions the sweep says least about.
- 58 are not run: functions with no retail address of their own (the empty `efff5_*` bodies and other inlined helpers) and functions that take register arguments (listed in `static.txt`).
- 18 differ, for these reasons:
  - Register-argument calls. Retail's D3D library takes arguments in registers; the C passes them on the stack, so in the harness the retail D3D body reads the wrong values from the C's call (`xb_SetRenderState`, `xb_SetMappedRenderState`, `xb_SetTextureStageState`). `xb_AsciiToSjis` takes its own argument in `al`, which the harness does not set. For a port this changes nothing.
  - The C runtime. `xb_LoadPanTables` calls `fopen`; retail's is the XDK's, which crashes in the harness, while the C gets the host's.
  - Uninitialized data. `dispButtonImage` and `xb_DrawExitScreen` queue a whole sprite of which they set only two vertices (in retail too); the unset bytes are stack garbage and differ. `xb_GetImagePixel` returns an unset value for an unknown pixel size, on both sides.
  - Floating point. `ADX_GetCoefficient`: retail's CRI code keeps intermediates on the x87 stack; the C is written in double and still rounds differently on some inputs. (Retail's Xbox colour conversion rounds with `cvtss2si`, which `xb_SaturateColor` reproduces.)
  - Out-of-range input. `Pal_Cursor_Put` with a type above 2 and `Menu_Task` with a random task read past their tables. `Setup_Letter_C4`, `kotp_06000`, `xb_mwsnd_MixPanCh0`/`Ch1`, `xb_wxci_SetRootDir` and `xb_wxfic_Create` differ only by one side crashing on a random pointer.
  - Unexplained: `Screen_Adjust` showed two trials writing different bytes at 0x7BD602 in one run, which other seeds do not reproduce.
